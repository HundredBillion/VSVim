# VSVim: an agent-aware PR review workspace

Date: 2026-10-16
Status: Architecture and written PRD approved by David; design hardening in progress.
Owner: David (DMI)

## Problem statement

Developers need to understand and review code produced by agents. A stream of
terminal output does not provide a comfortable view of the complete proposed
change, its review discussions, or its relationship to the target branch.
Constantly moving views also interrupt careful reading.

VSVim is a public, independent, batteries-included Neovim distribution designed
around reading and reviewing pull requests. It combines a VS Code visual target
inside Sprite with modal editing, agent-follow, and a separate LLM reviewer.
AstroNvim and LazyVim are product references, not distribution dependencies.

## Product outcome

The first working experience places Codex in Sprite's left terminal pane and
VSVim in its right pane. The developer sees the complete PR-oriented diff while
following Codex's activity. Deliberate navigation pauses following. A visible
button and keyboard command resume it at the agent's current known location.

The public release adds a separate reviewer conversation, developer-approved
patches, CRP beta findings and discussions, and GitHub comment reading and
publication. Core functionality also works in ordinary terminals on macOS and
Linux. Sprite supplies the richer native presentation.

## Vocabulary

| Term | Meaning |
| --- | --- |
| Target branch | The branch the PR would merge into; use the actual PR target when available, otherwise the repository default or an explicit user selection. |
| Review baseline | The merge-base revision used for the comparison with the target branch. |
| Local review | Proposed changes including current local work, which can differ from the published PR. |
| Published review | The revision and locations understood by the Git host for the remote PR. |
| Coding agent | The session modifying the project; Codex is the first supported agent. |
| Reviewer | A separate LLM conversation that explains code and proposes changes. |
| Proposal | A previewable set of additions, edits, or deletions awaiting developer application. |
| Follow | Navigation driven by activity from the selected coding-agent session. |
| CRP | The editor-independent Code Review Protocol for review data interchange. |

## User stories

1. As a new user, I want a complete editor setup so I can start working without assembling plugins.
2. As an existing Neovim user, I want an isolated installation so trying VSVim preserves my current setup.
3. As a Sprite user, I want VS Code-like visuals so navigation feels familiar.
4. As a terminal user, I want the same review capabilities without requiring Sprite.
5. As a developer, I want modal editing plus familiar commands for search and panels.
6. As a reviewer, I want all changes compared with the PR target rather than just the last agent edit.
7. As a reviewer, I want local-only changes distinguished from changes already published on the PR.
8. As a developer, I want VSVim to follow Codex running in another Sprite pane.
9. As a developer, I want to attach to a session I launched independently.
10. As a reader, I want navigation and discussion to pause following without stopping the coding agent.
11. As a reader, I want to resume at the current activity rather than replay every missed navigation event.
12. As a reviewer, I want a diff that adapts to the pane width and preserves my place when the layout changes.
13. As a reviewer, I want explanations from an LLM without interrupting the coding session.
14. As a developer, I want to preview reviewer-proposed file creation, edits, and deletion before applying them.
15. As a developer, I want stale proposals blocked so they cannot overwrite newer work.
16. As a reviewer, I want findings and conversations attached to the relevant code.
17. As a reviewer, I want outdated comments distinguished from confirmed resolutions.
18. As a GitHub user, I want to read, reply to, and publish PR comments from VSVim.
19. As a Git user, I want local review to work without a supported hosting integration.
20. As a user, I want customization and updates that preserve my configuration.

## Approved architecture

| Module | Owns |
| --- | --- |
| VSVim | Installation, update policy, defaults, hybrid mappings, theme, plugin composition, and workspace commands. |
| svgtree.nvim | Default file explorer with Sprite and ordinary-terminal presentations. |
| sprite.nvim | The existing bridge to Sprite's native presentation capabilities. |
| scm.nvim | Repository and PR navigation, review state, findings, discussions, host integration, and follow coordination. |
| Separate diff plugin | Adaptive comparison rendering, reading position, annotation placement, and patch previews. Its public name is chosen during its focused design. |
| CRP module inside SCM initially | Protocol validation, review-message handling, persistence, and comment reconciliation. The protocol specification remains independent. |

The diff viewer is separately installable. It receives comparisons and review
annotations through a small interface; it does not own Codex or GitHub clients.
SCM owns the review session and supplies the viewer with the necessary state.
VSVim integrates the plugins rather than duplicating their functionality.

Snacks is not a VSVim dependency. SCM's existing UI-free repository core is the
starting point for its replacement terminal and Sprite presentations. Existing
standalone plugin users must be considered in the migration plan; changing
their setup is not implicitly authorized by adding VSVim.

Coding-agent activity, reviewer providers, and Git hosting have separate
adapter interfaces. Codex is the first coding-agent activity integration and
GitHub the first host integration. The reviewer is LLM-agnostic from its first
release, with no required provider, Codex default, or single-provider launch
phase. Keep external assumptions out of rendering and CRP; expose unsupported
capabilities explicitly rather than pretending all integrations are identical.

## Required behavior

### Installation, editing, and presentation

- Support macOS and Linux. A first launch installs the bundled Neovim plugins
  and gives actionable guidance for external prerequisites; it does not imply
  automatic installation of every language tool or a Codex subscription.
- Preserve an existing Neovim configuration and separate VSVim configuration,
  state, and plugin data. Allow user overrides and reproducible plugin versions.
- Include common editing essentials: file/text search, completion, language
  diagnostics, syntax support, formatting integration, and Git navigation.
  Exact dependencies and language defaults belong in the foundation design.
- Use svgtree.nvim as the default explorer. Coordinate explorer and SCM panel
  focus without depending on Snacks.
- Retain Neovim modes and leader mappings. Add familiar shortcuts where the
  platform supports them; every essential action has a terminal-safe mapping.
- In Sprite, target VS Code's editor shell, explorer, source-control panel,
  typography, spacing, icons, tabs, and review layout. Capture a specific VS
  Code reference before visual implementation; exact matching is not an
  unbounded promise to reproduce every VS Code extension or dialog.
- Ordinary terminals retain diff review, follow controls, findings, discussions,
  and proposal application. Use text and terminal rendering when native
  presentation is unavailable.

### PR comparisons and diff reading

- Resolve the actual PR target when known. Otherwise use the repository default
  branch or a user-selected target; never silently assume a branch named main.
- Compare from the merge base to the proposed state. Include branch commits and
  local working changes, including relevant new files. Do not show unrelated
  target-branch advances as changes authored in the PR.
- Display the baseline and distinguish local from published state. Refreshing
  a baseline or a published revision must not silently move an existing draft
  comment to different code.
- Automatically recompute the baseline and hot reload the comparison as soon
  as relevant local changes are detected, including rebases and target-ref
  updates. No refresh button or approval is required. Remote changes become
  observable through host events or fetching; do not imply instantaneous
  knowledge of an unfetched remote revision. Discard superseded computations
  so an older result cannot replace a newer comparison.
- Adapt between side-by-side and unified presentation based on available width.
  Provide a manual override and preserve the selected location and thread.
- Represent renames, deletions, new files, and unsupported binary comparisons
  explicitly. Never interpret a failed comparison as an empty change set.

### Following an agent

- Prioritize Codex in Sprite's left pane and VSVim in the right pane. Support
  independent session launch and attachment as well as a coordinated workflow.
- Track one selected coding session initially. The reviewer conversation must
  not become a follow target merely because it is also an LLM session.
- Distinguish agent activity from filesystem changes. Filesystem events alone
  must not be presented as proof of agent identity or exact activity location.
- Pause on deliberate navigation, selection, editing, or review interaction.
  Rendering changes caused by follow itself must not trigger an immediate pause.
- Pausing follow pauses agent-driven navigation, not comparison updates. Hot
  reload while preserving the current file and reading position by code context
  where possible. If that context disappears, remain in the current review and
  indicate the change rather than jumping to the agent's file. Preserve draft
  text and its original revision; invalidate a stale code selection rather than
  silently attaching it to different code.
- Resume loads current content and jumps to the current known file/hunk. If the
  agent is idle, show its last known location with an idle indication. If activity
  is unavailable, say so rather than inventing a current location.
- Disconnection or agent failure leaves local review usable and explains the
  follow status. File refresh must never discard an unsaved developer buffer.

### Separate reviewer and controlled changes

- Let the developer configure the reviewer provider/model independently of the
  coding agent. Support multiple provider backends at initial release rather
  than postponing provider choice to a later milestone. Keep credentials and
  connection settings separate from review state and never silently fall back
  to another provider. Local model endpoints must be accommodated by the
  interface; actual compatibility is established through adapter validation.
- Normalize provider responses into the same explanations, findings, and
  proposed changes. Provider selection must not change approval enforcement or
  require changes to the diff viewer. Document supported integrations and
  capability limits; LLM-agnostic does not imply every model or API works
  without a compatible adapter.
- Run reviewer analysis on demand through an explicit review request or question.
  Agent activity, file changes, baseline refreshes, and resuming follow must not
  start LLM analysis automatically. Stale findings or proposals can be flagged
  without rerunning the reviewer; refreshing that analysis is a developer action.
- Supply a separate reviewer conversation with selected code, the relevant
  before/after context, and applicable review discussion.
- Permit reading and proposals that create, edit, or delete files. The reviewer
  has no unapproved write path to the working project, including indirect tool
  execution. The implementation must enforce this, not merely prompt for it.
- Show the affected files and patch before application. Applying a proposal
  requires an explicit developer action and checks against the reviewed content.
- Allow approval and application of individual hunks, with an explicit Apply
  all shortcut for the remaining proposal. Keep unapplied hunks available and
  clearly distinguish applied, pending, and stale hunks. Revalidate each selected
  hunk against current content, including changes from earlier applications.
- File creation and deletion require explicit file-level approval: a partially
  selected text hunk must not silently create or delete an entire file. Surface
  dependencies between changes rather than implying every hunk is independent.
- If affected content or unsaved buffers have changed, refuse blind application
  and require a refreshed proposal. Do not report partial application as success.
- Applying a local proposal does not commit, push, publish a comment, or resolve
  a review thread. Those are separate actions.

### CRP beta and GitHub

- Support the asynchronous findings/response workflow and the selected comment
  and change-request behavior needed by this release. Do not claim full CRP
  Level 2 or Level 3 conformance without their complete requirements.
- Finalize versioned message schemas and valid examples before implementing
  interchange. Invalid or unsupported messages must not corrupt review state.
- Keep code locations tied to the revision they describe. Uncommitted changes
  need a snapshot/location model separate from commit-linked identities.
- Preserve the handoff's distinction between active, archived, resolved, and
  superseded comments. Code changing does not prove the concern was resolved.
- Keep review metadata out of tracked project files. Determine the actual Git
  metadata location so worktrees are supported rather than assuming .git is a
  directory. No cloud synchronization is required for the beta.
- GitHub is the first host adapter. Read comments and replies, compose drafts,
  and send new comments or replies only through explicit developer action.
- Publish against the correct remote PR revision. Keep comments on local-only
  code local until they can be correctly anchored to published code.
- On publication failure, preserve the draft and expose the outcome. Avoid
  duplicating comments on retry after an uncertain network response.
- Without GitHub access, local comparisons and local review remain available.

## Delivery sequence and research gates

This is a release-level PRD, not a single implementation plan. Produce focused
plans for the milestones below, preserving the approved ownership split.

| Milestone | Deliverable | Evidence required before dependent implementation |
| --- | --- | --- |
| 1. Foundation | Independent distro, editing essentials, svgtree, Sprite integration, Snacks-free SCM | Dependency/version choices; clean startup in both presentations; migration plan for SCM users. |
| 2. PR reading | Separate adaptive diff plugin integrated with SCM | Comparison fixtures covering merge-base, local and published states, renames, deletion, and layout changes. |
| 3. Codex following | Two-pane workflow, attach, pause, and resume | Verify supported Codex launch/attach and activity mechanisms against installed tooling and official documentation. |
| 4. Reviewer proposals | Provider-neutral conversation with multiple backends and controlled patch application | Validate the same review and approval workflow across distinct provider backends, including stale content, new files, and deletion. |
| 5. CRP and GitHub | Beta interchange, local review state, remote threads and publication | Authoritative beta schemas; commit/snapshot reconciliation rules; correct remote comment anchoring. |
| 6. Public release | Visual parity work, installation/update docs, platform validation | Reference captures, macOS/Linux checks, terminal fallback, and complete review workflow. |

Resolve these uncertainties through bounded investigation rather than assuming
the handoff supplies executable contracts:

- Codex activity and attachment: identify a supported mechanism and its actual
  granularity. A limitation affecting the promised experience requires an
  explicit design revision before building a misleading substitute.
- CRP: reconstruct and approve missing schemas; settle transport, versioning,
  validation limits, and the release's supported message subset.
- Reviewer providers: select and validate a multi-provider integration strategy
  before implementation. Establish supported backends, local-endpoint support,
  capability reporting, and consistent approval enforcement without privileging
  Codex or postponing multi-provider support.
- Comment identity: test patch identity and contextual matching against real
  histories, including amend, rebase, squash, repeated text, and worktrees.
  Ambiguous matches must not silently move comments or mark them resolved.
- Sprite visual scope: compare native capabilities with the selected reference
  and identify any necessary Sprite changes before promising pixel parity.

## Acceptance and verification

Verify behavior through the public plugin interfaces and complete user flows.
Reuse SCM's separation of repository state from presentation, sprite.nvim's
protocol fixtures, and svgtree.nvim's visual-reference approach where applicable.
Do not use private function shape as the definition of correctness.

The release must demonstrate:

1. A clean isolated install on macOS and Linux, without Snacks or replacement of
   an existing Neovim setup; plugin updates preserve user configuration.
2. The same essential review actions in Sprite and an ordinary terminal.
3. Correct PR comparison when the target branch advances, when the PR targets a
   non-default branch, and when the working tree includes new or deleted files.
4. Adaptive diffs and manual toggling without losing the selected code/thread.
5. A real Codex edit opening the relevant comparison, a deliberate user action
   pausing it, and resume jumping to the latest known activity.
6. Paused reading and unsaved developer work surviving external edits and agent
   disconnects without navigation takeover or loss. Rebase and target-ref
   updates refresh the baseline automatically even while follow is paused;
   obsolete comparison results cannot overwrite the latest result.
7. Reviewer questions that leave the coding session independent; create/edit/
   delete proposals remaining unapplied until explicit approval. Live changes
   and baseline refreshes cause no reviewer calls without a developer request.
   Run the same explanation/proposal/approval scenarios across at least two
   distinct provider backends, independently of the coding-agent session.
8. A stale proposal failing safely, including changes made by Codex after preview.
   Applying one hunk leaves unselected changes unapplied; later applications
   revalidate against the updated file. File creation/deletion remain explicit.
9. Valid CRP fixtures rendering findings; invalid messages leaving existing state
   intact; explicit response actions producing the appropriate messages.
10. Changed code marking comments outdated rather than claiming human resolution;
    uncertain location matches staying visible for human attention.
11. GitHub comments loading and explicit sending succeeding against the correct
    published revision; failed sends preserving drafts without duplicate retries.
12. Reference-based visual review in Sprite and keyboard navigation checks in
    terminal mode. A green headless test is not proof of visual equivalence.

## Later roadmap and exclusions

- Other coding-agent follow integrations and Git hosts follow the first Codex
  and GitHub adapters. Reviewer provider choice is part of the initial release,
  not this later roadmap.
- Human collaboration comes later: shared PR review, then synchronized pair
  editing, screen sharing, and voice.
- An agent-management sidebar inspired by herdr is later work.
- Windows, cloud orchestration, paid plans, vendor outreach, and hosted editor
  infrastructure are outside this release.
- Execution-trace playback, impact/layer scoring, review timeline scrubbing,
  and complete real-time CRP collaboration are not first-release requirements.
- No automatic application of reviewer changes, unsolicited GitHub publication,
  or automatic resolution based solely on code changes.
